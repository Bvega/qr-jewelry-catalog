# 8. RESERVE BY MESSAGE EXPERIENCE

## 8.1 Detail-page reservation panel

Add a clear reservation section on Find Details.

Required heading:

```text
Reserve This Find
```

Required primary action:

```text
Reserve by Message
```

Required supporting statement:

```text
The owner confirms availability manually.
```

Required fulfillment statement:

```text
Payment is cash. Local pickup details are arranged by message after availability is confirmed.
```

Do not imply that clicking the button completes or guarantees a reservation.

## 8.2 Available state

For `available` Finds:

- primary action is enabled;
- activate the configured reservation flow;
- include exact title, public ID, and current link;
- expose success/cancel/failure feedback accessibly.

## 8.3 Reserved state

For `reserved` Finds:

- do not offer an active reservation submission;
- display:

```text
This Find is currently reserved.
```

- keep sharing, QR, Related Finds, and navigation available.

## 8.4 Sold state

For `sold` Finds:

- do not offer an active reservation submission;
- display:

```text
This Find has been sold.
```

- keep the public detail page accessible;
- keep sharing, QR, Related Finds, and navigation available.

## 8.5 Web Share behavior

When available, use the native browser share interface with:

- Between Us reservation-request title;
- generated reservation message;
- current detail URL.

Do not assume a specific messaging application.

User cancellation is not an error.

## 8.6 Clipboard fallback

When Web Share is unavailable or fails for a non-cancellation reason:

- copy the complete reservation message and URL;
- provide a visible and screen-reader-accessible confirmation;
- explain that the visitor can paste it into their preferred messaging application.

If clipboard access also fails:

- display the generated message in a selectable text region;
- provide an honest failure instruction;
- do not silently fail.

## 8.7 Accessibility

Required:

- primary action is a real button or valid channel link;
- at least 44px mobile target;
- visible focus;
- status feedback uses a polite `aria-live` region;
- disabled state is communicated in text, not color alone;
- no automatic focus jump unless required for accessible feedback;
- no modal is required;
- if a dialog is introduced, it must follow accessible dialog behavior.
